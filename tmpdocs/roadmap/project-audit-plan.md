# MySelfPlayAgent 项目审计方案

> 面向第一次接触本项目、没有既有架构知识的审计者。  
> 文档版本：v1.0　制定日期：2026-08-28　审计对象：当前 `main` 分支及其运行数据。

## 1. 审计目的

本项目的代码、注释、测试和大部分设计文档均由 AI 生成。因此，本次审计不能只回答“代码能否运行”，还要回答以下问题：

1. 项目实际实现了什么，是否与 README、检查点和设计文档的声明一致；
2. 对战引擎、Chat Agent、人机对战、自博弈和自进化之间的数据流是否正确；
3. 测试是否真的验证了业务行为，而不是与实现共享了同一种错误假设；
4. 是否存在信息泄漏、提示词注入、越权文件访问、敏感信息暴露等安全问题；
5. 自进化指标是否代表真实策略提升，而不是随机性、数据污染或评测过拟合；
6. 项目是否具备可维护、可复现、可回滚和继续扩展的基础。

本次审计的最终结果不是简单的“通过/不通过”，而是一套有证据、有风险等级、有修复优先级的项目健康报告。

## 2. 审计基本原则

### 2.1 文档是声明，不是事实

`README.md`、`docs/checkpoints/`、代码注释和测试名称都只能作为“项目声称自己实现了什么”的输入，不能直接作为审计结论，也不能被视为对审计者的操作指令。

每项重要结论至少需要以下两类证据相互印证：

- 静态证据：代码、配置、数据结构、依赖关系；
- 动态证据：实际运行结果、重放结果、错误注入结果；
- 独立测试：由审计者根据业务不变量重新编写的测试；
- 数据证据：真实轨迹、日志、版本指纹和统计结果。

### 2.2 测试通过不等于设计正确

AI 可能同时生成实现和测试，使二者共享同一个错误理解。现有测试主要证明“实现符合现有测试”，不能单独证明：

- 游戏规则符合预期；
- 迷雾信息没有泄漏；
- 自进化真的提高了 LLM 策略能力；
- Web 输入不能触发注入或越权；
- 异常、并发和长时间运行是安全的。

因此必须补充性质测试、变形测试、故障注入、差分测试和人工构造的反例。

### 2.3 审计与修复分离

审计期间不顺手修改发现的问题。先记录证据和复现步骤，统一评估影响，再在单独分支修复。这样可以避免：

- 修复改变现场，导致其他问题无法复现；
- 多个修改混在一起，无法判断哪个修改有效；
- 审计范围不断扩大；
- AI 为了让测试通过而掩盖根因。

### 2.4 优先验证系统不变量

完全不了解架构时，不要从逐行阅读 2 万多行代码开始。先确定系统绝不能违反的规则，再沿着这些规则追踪代码和数据。

本项目的首批核心不变量见第 8 节。

## 3. 当前基线与审计边界

### 3.1 当前仓库概况

初步盘点得到以下基线：

- 核心代码分为 `environment`、`rock_pvp_agent`、`ui` 三个包；
- 主要能力包括 Chat Mode、组队、人机对战、Agent 自博弈、自进化和观战；
- `src/`、`tests/`、`docs/` 中相关文件约 2.6 万行；
- 当前测试基线为 809 项通过；
- Git 里程碑从 M0–M4、E0–E7 延伸到 R0–R8；
- README 和部分文档仍停留在早期“仅 chat mode”或“84 tests”的描述，与当前代码存在时间差。

以上内容是审计起点，不代表对质量的认可。

### 3.2 纳入范围

- Python 后端、CLI 和配置；
- 对战数据、规则、状态机、随机数和重放；
- Chat Agent、Prompt、工具调用和 LLM 降级路径；
- 组队、人机对战、观战 Web/API；
- 自博弈、自进化、记忆、反事实、评测集、策略池和回滚；
- 前端输入输出和浏览器安全；
- 轨迹、队伍、注册表等本地文件；
- 测试有效性、依赖、构建、运行和文档一致性。

### 3.3 暂不纳入范围

- 未获得明确授权的真实用户数据；
- 第三方 LLM 服务提供商内部安全；
- 对游戏规则“是否百分之百还原官方”的版权或业务认定；
- 未部署到公网时的云基础设施和账号权限。

如果以后公开部署，应增加独立的网络、认证、速率限制和隐私合规审计。

## 5. 风险等级与证据状态

### 5.1 风险等级

| 等级 | 定义 | 示例 | 处理要求 |
|---|---|---|---|
| P0 致命 | 造成数据泄漏、任意代码/文件操作、核心评测完全失真 | LLM 读取不可见状态；路径逃逸；晋级指标无业务含义 | 立即停止相关功能，修复后全量复验 |
| P1 高 | 大范围错误结果、无法恢复、显著安全风险 | 重放不一致；跨用户数据串线；测试集回流训练 | 当前版本发布前修复 |
| P2 中 | 局部错误、可靠性或维护性明显不足 | 异常被吞、元数据缺失、并发覆盖文件 | 纳入最近修复周期 |
| P3 低 | 文档、可读性、诊断体验问题 | README 过期、错误信息不清楚 | 排期修复 |

风险等级由“影响 × 可触发性 × 可检测性”共同决定，不以代码行数决定。

### 5.2 证据状态

- `已证实`：有最小复现或可重复动态证据；
- `高度可信`：静态路径清晰，但尚未动态触发；
- `待验证假设`：存在风险迹象，需要设计实验；
- `已排除`：有反证或独立测试证明不成立；
- `无法判断`：缺少规则、样本或外部信息。

审计报告不得把“待验证假设”写成已确认漏洞。

## 6. 先建立一张可理解的系统地图

建议按下面顺序理解项目，而不是按文件名字母顺序阅读：

```text
用户
 ├─ CLI ───────────────┐
 └─ Web UI / REST / SSE│
                       ▼
              ChatAgent / Battle UI
                │             │
                │             ├─ 人类动作
                │             └─ LLM/FakeLLM/Playbook 动作
                ▼                         │
          Prompt + Tools                  ▼
                │                 BattleSession / Engine
                ▼                         │
          外部 LLM 服务              事件、状态、轨迹
                                          │
                            ┌─────────────┴─────────────┐
                            ▼                           ▼
                       Replay/Analysis            Self-play/Evolution
                                                        │
                                              Memory/Playbook/Pool
```

初次阅读推荐路径：

1. 启动和配置：`pyproject.toml` → `rock_pvp_agent/__main__.py` → `config.py`；
2. Chat：`prompts.py` → `tools.py` → `llm.py` → `agent.py`；
3. 对战：`models.py` → `session.py` → `engine.py` → `match.py`；
4. 迷雾和重放：`view.py` → `visibility.py` → `replay.py`；
5. 对战玩家：`battle/player.py` → `battle/selfplay.py` → `battle/store.py`；
6. 自进化：`evolution/run.py` → `analysis.py` → `credit.py` → `reflect.py` → `editor.py` → `pool.py`；
7. 记忆和长期运行：`memory.py` → `valuefn.py` → `ops.py`；
8. Web：`ui/server.py` → 各路由 → 对应静态 JavaScript。

每读完一个模块，只记录五件事：输入、输出、持有的状态、外部副作用、失败方式。

## 7. 分阶段审计流程

### 阶段 A：冻结基线

目标：保证所有后续结果能够追溯到同一个代码和数据版本。

操作：

```bash
git status --short
git rev-parse HEAD
git log --oneline -20
uv sync --all-extras --frozen
uv run python -m rock_pvp_agent --version
uv run pytest -q
uv run pytest --cov=rock_pvp_agent --cov=environment --cov=ui --cov-report=term-missing
```

记录：

- 操作系统、Python 和 `uv` 版本；
- commit ID、未提交文件和数据目录；
- 测试数量、耗时、覆盖率和警告；
- 是否配置 LLM key，但不得记录 key 本身；
- 当前模型、规则、数据和 Playbook 指纹。

Gate A：任意审计者能在干净环境复现安装和测试；如果失败，先记录为构建/复现问题，不进入功能结论。

### 阶段 B：建立“声明—实现—验证”矩阵

目标：发现文档过期、功能漏实现和“只存在于注释中的功能”。

对 README、CHANGELOG、checkpoint、CLI 帮助和页面逐项建立矩阵：

| ID | 功能声明 | 代码入口 | 现有测试 | 独立运行证据 | 结论 |
|---|---|---|---|---|---|
| REQ-001 | 无 key 时离线降级 | 待填写 | 待填写 | 待填写 | 待审计 |
| REQ-002 | LLM 只能看到迷雾视角 | 待填写 | 待填写 | 待填写 | 待审计 |
| REQ-003 | 轨迹可确定性重放 | 待填写 | 待填写 | 待填写 | 待审计 |
| REQ-004 | D_test 不参与优化 | 待填写 | 待填写 | 待填写 | 待审计 |

重点搜索：

```bash
rg -n "TODO|FIXME|HACK|NotImplemented|已实现|安全|绝不|保证" src docs tests
rg -n "add_api_route|@router|@app|add_parser|add_argument" src
```

Gate B：所有对外能力都有实际入口、明确所有者和至少一种验证办法；无法找到实现的声明标为“文档失真”。

### 阶段 C：架构和依赖审计

目标：验证模块边界、依赖方向和共享状态是否可控。

检查：

- `environment` 是否可以脱离 UI 和 LLM 独立运行；
- 核心层是否反向导入 `ui`；
- 是否存在循环导入、运行时临时导入掩盖的耦合；
- 配置、LLM 客户端、随机数和缓存是否是隐式全局状态；
- CLI、Web、人机对战和自博弈是否走同一套核心规则；
- 同一概念是否有多个实现，例如事件过滤、队伍校验、玩家降级；
- 文件读写是否集中封装，还是散落在业务代码中；
- 异常是否被宽泛捕获后静默忽略。

AI 生成代码特别容易出现“看起来分层、实际上重复实现”的情况。发现两个相似函数时，要构造同一输入进行差分测试，而不只比较函数名和注释。

Gate C：输出实际依赖图、状态所有权表和至少一张端到端数据流图；所有跨层依赖都能解释原因。

### 阶段 D：对战引擎和数据正确性

目标：确认游戏状态转移合法、确定、可重放，而且 UI、自博弈和评测使用相同语义。

按以下顺序审计：

1. 数据源和版本：精灵、技能、属性克制、特性、队伍构建；
2. 合法动作：技能、换人、道具、补位；
3. 回合顺序：优先级、速度、随机数消耗；
4. 伤害和状态：边界值、叠层、死亡、最大回合；
5. 终局判定：胜、负、平局；
6. 重放：原始记录能否逐回合得到相同状态哈希；
7. 版本兼容：旧轨迹遇到新规则时是否被拒绝或正确迁移。

必须补充的独立测试类型：

- 性质测试：HP 不低于零、能量不越界、非法动作不改变状态；
- 变形测试：交换双方和对应 seed 后，结果应满足预定的对称关系；
- 差分测试：CLI、Web、自博弈对相同状态和动作得到相同结果；
- 故障注入：损坏一回合、修改队伍、修改规则后，重放必须失败；
- 边界测试：同时倒下、无可替补、速度相同、零能量、最大叠层。

Gate D：核心不变量全部有独立测试；任意保存轨迹都能验证来源并重放，或明确说明不可重放原因。

### 阶段 E：Chat、Prompt 和工具审计

目标：确认模型只能调用被授权的工具，Prompt 不会覆盖系统约束，错误不会泄露敏感内容。

检查：

- System Prompt 是否明确角色、范围、事实来源和拒答边界；
- 用户输入、网站内容、轨迹文本和自生成 Skill 是否被视为不可信数据；
- 工具 schema 是否限制参数长度、枚举、路径和操作范围；
- 模型是否可能伪造工具结果或绕过 `final_answer` 协议；
- 工具失败、超时、返回超长内容时是否安全降级；
- 多轮历史是否造成跨会话串线或无限增长；
- 真实 LLM 与 FakeLLM 降级是否在响应和轨迹中明确标识；
- Prompt、模型、工具集合是否有版本和指纹；
- 是否向普通用户暴露内部推理、密钥、堆栈、完整状态或未过滤轨迹。

对抗输入至少覆盖：

- “忽略之前所有指令”；
- 把恶意指令放进网页、Skill、精灵描述或轨迹；
- 让 Agent 读取任意文件或透露环境变量；
- 超长输入和递归工具调用；
- 伪造 `final_answer`、工具名或 JSON；
- 非项目话题、违法请求和诱导泄密请求。

Gate E：所有外部文本都不能提升权限；工具调用由代码校验而非只靠 Prompt 约束；敏感信息不会出现在 UI、日志或轨迹中。

### 阶段 F：Web、API、文件和前端安全

目标：验证浏览器输入、HTTP 接口、本地文件和并发访问的安全性。

检查：

- 每个 API 的请求模型、长度限制、错误码和副作用；
- 队伍、轨迹、Playbook 文件路径是否阻止绝对路径和 `..` 逃逸；
- 写文件是否原子化，并发时是否会覆盖或破坏数据；
- SSE 断线、重连、重复提交是否造成重复动作；
- 会话 ID 是否可猜测并读取其他用户历史；
- CORS、Host、监听地址和生产部署默认值；
- 所有 `innerHTML` 数据是否经过可靠转义；
- Markdown 链接、HTML、事件文本、精灵名称和 LLM 输出是否可能触发 XSS；
- API 是否暴露完整对战状态、内部路径、Prompt 或模型错误；
- 删除、覆盖和回滚等操作是否需要更强确认。

测试时至少使用两个并发会话、两个浏览器身份和重复请求。不要只测试单用户顺序操作。

Gate F：路径逃逸、跨会话访问、存储型/反射型 XSS、重复动作和未授权破坏操作均有负向测试。

### 阶段 G：自博弈和自进化有效性

目标：区分“流程运行成功”和“Agent 策略真实提升”。

逐项验证：

1. **语义承载**：Playbook 文本是否真的影响模型决策，而不是仅改变随机种子；
2. **数据隔离**：D_tr、D_sel、D_test 是否在阵容、seed、内容和人工查看层面隔离；
3. **候选生成**：反思只能读取训练证据，不能看到测试答案；
4. **反事实**：代理尾策略是否足以代表当前 Agent，误差如何估计；
5. **记忆闭环**：经验是否被检索、展示、采用并在赛后回填效果；
6. **价值模型**：训练、验证是否按完整对局或阵容族隔离；
7. **晋级门**：是否要求统计显著、关键切片不回退和历史策略不循环克制；
8. **模型变化**：更换基础模型后是否全量重评；
9. **成本匹配**：候选与基线是否使用相同调用预算、温度和超时；
10. **可复现性**：报告能否由指定 commit、模型、数据、seed 和 Playbook 重新生成。

有效提升声明必须包含：

- 基线和候选版本；
- 基础模型及参数；
- 数据、规则和引擎指纹；
- 对手组成、阵容族和 seed；
- 样本量、胜率和置信区间；
- 运行成本和失败率；
- D_sel 与锁定 D_test 的结果；
- 至少一次独立复验。

如果无 key 路径使用确定性随机代理，只能判定 Harness 可运行，不能据此声明 Playbook 或 LLM 变强。

Gate G：只有真实模型在锁定测试集上重复提升、关键切片无明显回退时，才能使用“自进化有效”的表述。

### 阶段 H：测试体系有效性

目标：评价测试是否会在代码被故意破坏时失败。

检查：

- 覆盖率是否集中在简单 getter 和序列化，而遗漏核心分支；
- 测试是否复制实现算法来计算预期结果；
- 是否过度 mock，导致实际依赖和协议没有运行；
- 是否只断言 HTTP 200、文件存在或字段非空；
- 是否依赖执行顺序、真实时间或全局缓存；
- 是否存在 flaky、被跳过或极慢的测试；
- FakeLLM 是否覆盖真实返回格式的变化和错误场景；
- 前端是否只有后端测试而没有浏览器行为验证。

建议选择以下关键模块做小规模变异测试：

- 反转属性克制倍率；
- 删除事件过滤；
- 让非法动作通过；
- 忽略 replay 的 state hash；
- 交换 D_sel 与 D_test；
- 让晋级门始终返回通过；
- 移除 HTML 转义。

不提交这些故意破坏，只观察现有测试是否能发现。若测试仍全部通过，就记录相应测试缺口。

Gate H：核心安全和业务规则的变异能够被测试捕获；测试失败信息能定位到具体不变量。

### 阶段 I：依赖、构建和运维

目标：确认项目可以安全安装、部署、升级和恢复。

检查：

- `uv.lock` 与 `pyproject.toml` 是否一致；
- 包构建后是否包含数据文件和前端静态资源；
- 直接源码运行和安装 wheel 后运行是否一致；
- 依赖是否存在已知漏洞、废弃 API 或不兼容升级；
- `.env`、日志、轨迹和错误报告是否可能包含 secret；
- 进程中断、磁盘满、文件损坏和模型超时时能否恢复；
- 注册表回滚是否恢复完整 Playbook、配置和数据指纹；
- 长时间运行的成本上限、暂停条件和告警是否有效。

可在隔离环境中增加：

```bash
uv build
uv pip check
uv run pip-audit
```

`pip-audit` 需要作为独立审计工具安装；不要为了让命令通过而随意升级生产依赖。

Gate I：从锁文件可重复构建；恢复演练成功；密钥不进入包、Git、日志或轨迹。

### 阶段 J：形成结论和修复计划

每个发现必须包含：

```markdown
## AUD-XXX：简短标题

- 风险等级：P0/P1/P2/P3
- 证据状态：已证实/高度可信/待验证假设
- 影响范围：
- 前置条件：
- 复现步骤：
- 实际结果：
- 预期结果：
- 根因位置：文件和行号
- 证据：日志、测试、轨迹或截图
- 建议修复：
- 修复验收：至少一个回归测试和一个负向测试
- 可能副作用：
```

修复顺序：P0 → P1 → 影响评测可信度的问题 → 数据迁移问题 → P2 → P3。每修复一组问题，重新执行受影响模块测试和全量测试，最后重复锁定测试集评测。

## 8. 本项目必须验证的核心不变量

### 8.1 对战与迷雾

- LLM 只能看到所属侧的 `view(side)`；
- 回合事件进入 LLM 前必须经过 `filter_events_for(side, ...)`；
- 观战者可见完整状态不能反向污染玩家输入；
- 非法动作不能改变任何状态或随机数流；
- 相同初始数据、动作序列和 seed 必须产生相同状态哈希；
- 重放不得忽略缺失回合、篡改动作或版本不匹配。

### 8.2 Chat 和工具

- 用户、网站、轨迹和 Skill 中的指令都不能覆盖 System Prompt；
- 模型不能调用未注册工具；
- 所有工具参数由代码验证；
- 未配置 key 的降级结果必须明确标识，不得伪装为真实模型；
- 会话 A 的历史不能被会话 B 读取；
- 内部推理、密钥和堆栈不得出现在普通响应中。

### 8.3 文件和数据

- 用户提供的路径不能逃出允许目录；
- 保存采用原子写，冲突和损坏可检测；
- 轨迹必须记录实际玩家、模型、规则、数据和 Playbook 版本；
- 人机轨迹和自博弈轨迹保留来源标签，不能无条件混合；
- 数据版本不兼容时必须拒绝训练或显式迁移。

### 8.4 自进化

- D_test 内容不进入反思、候选生成、早停和健康门；
- 训练和验证不能使用同一对局的不同回合样本；
- 候选与 Champion 使用相同预算和评测条件；
- 晋级不能仅由随机序列变化造成；
- 经验被检索后才增加 `n_used`，实际采用后才增加 `n_adopted`；
- 每条 Skill 都能回溯到支持证据和反例；
- 模型、规则或数据变化后，旧分数不能直接与新分数比较。

## 9. AI 生成项目专项检查清单

### 9.1 代码层

- [ ] 注释描述的行为与函数实际行为一致；
- [ ] 不存在只为测试制造信号、但没有业务语义的代理实现；
- [ ] 相同概念没有多个逐渐分叉的实现；
- [ ] 没有未使用的类、参数、指标或配置开关；
- [ ] 默认值不会悄悄关闭核心能力；
- [ ] 降级路径不会被记录成真实能力；
- [ ] 宽泛 `except` 不会吞掉数据损坏和安全异常；
- [ ] 魔法数字都有规则来源和边界测试；
- [ ] 函数名中的 `safe`、`validate`、`deterministic` 都有反例验证；
- [ ] 第三方 API 调用符合当前依赖版本，而不是模型记忆中的旧接口。

### 9.2 测试层

- [ ] 测试不是把实现代码复制一遍再比较；
- [ ] 关键错误路径不是全部 mock；
- [ ] 断言验证业务结果，而不只是 `ok=True`；
- [ ] 测试覆盖并发、损坏输入、极端边界和恶意输入；
- [ ] 固定 seed 没有掩盖其他随机或模型不确定性；
- [ ] 测试数据与生产数据 schema 一致；
- [ ] 至少一组测试由需求不变量推导，而非从代码反推。

### 9.3 文档层

- [ ] README 功能、命令、测试数量和版本是当前状态；
- [ ] checkpoint 的“通过”能由当前 commit 重新验证；
- [ ] 设计计划明确区分已实现、部分实现和计划中；
- [ ] 安全声明带有测试或审计证据；
- [ ] 性能、胜率和提升声明包含完整评测上下文。

## 10. 首轮优先验证的风险假设

以下是根据当前结构提出的审计起点，不是最终漏洞结论：

1. **人机对战事件视角**：UI 返回给人类的事件经过过滤，但需要确认传给 LLM 对手的回合结果是否也按其视角过滤；
2. **离线 Playbook 指标语义**：确认文本变化是否只是改变 RandomPlayer 的种子，若是，则离线胜率不能证明文本策略提升；
3. **记忆闭环**：确认经验检索、`n_used/n_adopted` 和 Q 回填是否存在真实生产调用路径；
4. **价值模型验证泄漏**：确认 AUC 是否在训练样本本身计算，以及同一场对局的回合是否跨越训练/验证边界；
5. **D_test 间接污染**：虽然代码不把 D_test 输入优化器，但每个 epoch 展示结果可能导致人工反复据此调参；
6. **人机轨迹可追溯性**：确认是否保存实际玩家类型、模型、Playbook、规则和数据指纹；
7. **原始 strategy 输入**：确认用户提交的战术文本是否有长度、来源、版本和提示词注入防护；
8. **前端 `innerHTML`**：逐个追踪所有动态值是否经过转义，尤其是 LLM 回复、事件、队名、精灵名和文件名；
9. **思维过程暴露**：确认 `reasoning_content` 的展示、日志和持久化策略是否符合实际部署的隐私与安全要求；
10. **文档漂移**：README、CHANGELOG、docs 索引与当前 E/R 功能明显存在版本差，需要确认用户是否会按过期文档操作。

建议先处理 1–7，因为它们直接影响安全性和“自进化是否有效”的核心结论。

## 11. 新手执行节奏

不要试图一次完成全部审计。推荐每次只审计一个可以独立回答的问题。

| 审计轮次 | 重点 | 建议产物 |
|---|---|---|
| 第 1 次 | 冻结基线、跑通 CLI/Web/测试 | `00-baseline.md` |
| 第 2 次 | 系统地图、入口和数据流 | `01-system-map.md` |
| 第 3 次 | 对战不变量、迷雾和重放 | 发现记录 + 独立测试 |
| 第 4 次 | Chat、Prompt、工具和会话 | 威胁模型 + 对抗用例 |
| 第 5 次 | Web/API、路径、XSS、并发 | 接口清单 + 安全测试 |
| 第 6 次 | 自博弈、轨迹和记忆 | 数据血缘图 |
| 第 7 次 | 自进化指标和评测隔离 | 实验审计报告 |
| 第 8 次 | 测试质量和变异实验 | `05-test-gaps.md` |
| 第 9 次 | 构建、依赖、恢复和文档 | 运维/复现报告 |
| 第 10 次 | 汇总结论和修复排序 | `final-audit-report.md` |

每轮结束只允许三种结论：有证据通过、有证据失败、证据不足。避免使用“看起来没问题”。

## 13. 审计者的决策边界

审计者不需要先成为该项目专家，但需要坚持以下规则：

- 不理解的规则标记为“需要产品确认”，不要让 AI 自行补全业务事实；
- 不接受只有自然语言解释、没有代码路径或运行证据的结论；
- 不让负责实现的同一个 AI 成为唯一审计者；
- 可以让 AI 帮助定位和生成测试，但测试预期必须来自人工确认的不变量；
- 遇到 P0/P1 问题先停止相关功能，保留现场，再讨论修复；
- 所有删除、迁移、覆盖和回滚操作都必须单独审批并先备份。

这套流程的核心不是“把每一行代码都读懂”，而是让每一个重要系统承诺都能被独立证据验证、被反例挑战，并在失败时可追溯、可修复、可复验。
